# Coding Conventions

**Analysis Date:** 2026-04-19

## Naming Patterns

**Files:**

- TypeScript/TSX source under `src/` using `.ts` / `.tsx`.
- Next.js App Router: route segments as folders (`page.tsx`, `layout.tsx`, `route.ts`); dynamic segments `[slug]`, route groups `(frontend)`, `(payload)`.
- Payload collections: either `src/collections/<Name>/index.ts` with optional `hooks/` (for example `Comments/index.ts`, `Comments/hooks/applyCommentModeration.ts`) or single-file exports such as `src/collections/Media.ts`, `src/collections/Categories.ts`.
- React components: typically `index.tsx` inside a component folder (for example `src/components/Link/index.tsx`) or PascalCase filenames where a single file is exported.
- Config at repo root: `eslint.config.mjs`, `vitest.config.mts`, `playwright.config.ts`, `next.config.js`, `tsconfig.json`.

**Functions:**

- `camelCase` for functions and methods (`slugifyTitle`, `serializeComment`, `login`).
- Async handlers follow Next.js naming: `GET`, `POST`, `generateMetadata`, etc. in `route.ts` files.

**Variables:**

- `camelCase` for locals and parameters.
- `UPPER_SNAKE_CASE` for module-level constants (for example `DEFAULT_PAGE_SIZE`, `MAX_PAGE_SIZE` in `src/app/(frontend)/api/site-comments/route.ts`).

**Types:**

- `PascalCase` for types, interfaces, and React component props types (for example `CMSLinkType`, `LoginOptions` in `tests/helpers/login.ts`).
- `React.FC<Props>` appears for some components (for example `CMSLink` in `src/components/Link/index.tsx`).
- Generated CMS types: import from `@/payload-types` (generated by Payload).

## Code Style

**Formatting:**

- Prettier via `.prettierrc.json`: single quotes, trailing commas (`"all"`), `printWidth` 100, **no semicolons** (`"semi": false`).
- Match existing files: 2-space indentation in practice.

**Linting:**

- ESLint flat config: `eslint.config.mjs`.
- Extends `next/core-web-vitals` and `next/typescript` via `@eslint/eslintrc` `FlatCompat`.
- Notable rules: `@typescript-eslint/no-unused-vars` as **warn** with `_` prefix ignored for unused vars/args; `@typescript-eslint/no-explicit-any`, `ban-ts-comment`, `no-empty-object-type` as **warn**.
- Run: `pnpm run lint` (uses `next lint`); fix: `pnpm run lint:fix`.
- Ignore: `.next/` (see `eslint.config.mjs`).

**TypeScript:**

- `tsconfig.json`: `strict: true`, `moduleResolution: "bundler"`, `paths` for `@/*` → `./src/*` and `@payload-config` → `./src/payload.config.ts`.

## Import Organization

**Order (typical in this repo):**

1. Config or framework imports that must be first when required (for example `config from '@payload-config'`).
2. External packages (`payload`, `next/*`, `react`).
3. Internal absolute imports (`@/...`).
4. `import type { ... }` blocks often grouped after value imports or adjacent to related imports (see `src/components/Link/index.tsx`).

**Path aliases:**

- `@/*` → `src/*` (see `tsconfig.json`).
- `@payload-config` → `src/payload.config.ts`.

**Prescriptive guidance for new code:**

- Prefer `@/` for anything under `src/` instead of long `../../../` chains.
- Use `import type` for type-only imports where it keeps bundles clear (consistent with files like `src/components/Link/index.tsx`).

## Error Handling

**API route handlers (`src/app/**/route.ts`):**

- Validate input early; return `NextResponse.json({ error: '...' }, { status: 4xx })` for client errors.
- Parse JSON in `try/catch`; on failure return 400 with a short message (see `POST` in `src/app/(frontend)/api/site-comments/route.ts`).
- On Payload failures, catch and if `e instanceof APIError`, return `e.message` with `e.status`; otherwise map unknown errors to 500 with a generic or `Error` message (same file).

**Payload:**

- Prefer `APIError` from `payload` where applicable; use `overrideAccess: false` when enforcing user permissions in Local API (project rule; see handlers that pass `req` / auth context).

**Logging:**

- No shared structured logger detected in application code; errors surface via HTTP responses. `vitest.setup.ts` loads `dotenv/config` for tests only.

## Comments

**When to comment:**

- Short inline comments for non-obvious domain rules (for example Vietnamese slug normalization steps in `src/utilities/slugify.ts`).
- Block comments in config where the template explains removable UI hooks (`src/payload.config.ts`).

**JSDoc:**

- Used on selected test helpers and utilities (for example `tests/helpers/login.ts`, `tests/helpers/seedUser.ts`) with a one-line description.

## Function Design

**Size and structure:**

- Prefer early returns for validation (guard clauses) in route handlers.
- Extract small serializers/helpers next to the route when they clarify the response shape (for example `serializeComment` in `src/app/(frontend)/api/site-comments/route.ts`).

**Parameters:**

- Destructuring common for React components and helpers (`login` in `tests/helpers/login.ts`).

## Module Design

**Exports:**

- Named exports common for utilities and components (`export function slugifyTitle`, `export const CMSLink`).
- Payload collections export named config objects from `index.ts` files (for example `src/collections/Comments/index.ts`).

**Barrel files:**

- Component folders use `index.tsx` as the public export for that folder.
